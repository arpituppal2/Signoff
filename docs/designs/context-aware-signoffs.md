# Design: Context-Aware Sign-Offs (Read the Thread, Fit the Moment)

Generated by /office-hours on 2026-09-09
Branch: main
Repo: Signoff
Status: APPROVED
Mode: Builder

## Problem Statement

Signoff is a macOS menu-bar app that turns a click into an email sign-off. It generates
closers via Apple's on-device Foundation Models 3B. The output is bad in the specific ways
a small instruction-tuned model goes bad: redundancies, literally emitting the word
"comma," unfunny closers, and word salad.

The user's own diagnosis over repeated sessions is that the 3B isn't pointed at the right
register — it produces "generic AI closer" because nothing told it who the email is to and
what the thread's tone is.

## The Idea

"It fits the moment." Instead of making the user pick a bucket and hope the model doesn't
ruin it, the app reads the email thread being replied to, infers the register itself, and
generates a sign-off that matches: "Best regards," to a boss about a deadline; "later,
nerd" to a friend about weekend plans; "Thank you for your patience," to a client after a
tense thread.

Two facts make this feasible today: the thread is already in the composition window as
quoted text ("On Sep 9, Arpit wrote: …"), readable via the macOS Accessibility API; and
because register detection and generation both run on-device, the email content never
leaves the machine — a privacy position cloud tone-tools can't claim.

## Register Taxonomy

The classifier emits exactly one of the three **tone** registers. These are the existing
`BucketID` tone cases; the structural cases (`list`, `footer`) are out of scope, and
`generalLegacy` is a v1 migration alias, not a generation target.

| Register (`BucketID`) | Classifier signals | Example closer |
|---|---|---|
| `professional` | formal salutation, deadlines, numbers, titles, no emoji | "Best regards," |
| `standard` | casual tone, emoji, first names, humor | "later, nerd" |
| `unhinged` | in-jokes, all-caps, chaotic/celebratory energy | "(slaps keyboard)" |

The `unhinged` register is emitted at its `regular` `UnhingedLevel` (the enum has
`calm/regular/deranged/cynical`). Level selection is NOT part of this design — detection
picks the register only; the level stays fixed at `regular` until a future pass adds level
detection.

Fallback register: `standard`. When no thread text is available (fresh email, not a reply)
or the classifier is uncertain, generation falls back to `standard` at its normal
temperature — the current default-bucket behavior (`BucketID.standard`, `AppState.swift:41`).

Two naming/clarity corrections surfaced by engineering review:

- **"Register" here means a `BucketID` tone case, NOT the code's per-bucket sub-register.**
  The existing code already uses "register" for a different thing: `PromptTemplate.registers`
  (e.g. `professional` → `gratitude`/`respect`) and `AppState.preferredRegister`, keyed by
  `forcedRegister` cycling in `executeHybridGeneration` (`GenerationService.swift:290-352`).
  The classifier's output ("professional"/"standard"/"unhinged") is a `BucketID`; it does
  not slot into that sub-register mechanism. When the doc says "that register's existing
  instructions," it means the bucket's prompt template, not a sub-register.
- **`standard` becomes a real generation target.** Today `standard` short-circuits to a
  canned `QuoteSelector` quote with no model call (`GenerationService.swift:127-138`). The
  context-aware path must bypass that short-circuit so a casual thread gets a model-generated
  context-fit closer (the "later, nerd" example), not a canned quote. This is a deliberate
  change to a v1 choice, not a drop-in.

**Unhinged safety gate.** The classifier auto-selecting `unhinged` has a wrongness risk the
uncertainty fallback does not cover: a professional thread confidently misclassified
`unhinged` pastes "(slaps keyboard)" to a client. Guard: the classifier must meet a
confidence threshold (calibrated in the probe) before emitting `unhinged`, AND the chosen
register is surfaced in the popover so the user sees it before pasting — no
confident-but-wrong closer reaches the clipboard silently.

## Constraints

- Minimum target: M1 MacBook Air / A18 Pro, 8GB RAM.
- No cost (no paid API; the user wants "free free free").
- On-device is a hard requirement — email content must not leave the Mac.
- macOS 27 (already shipped).

## Premises

1. The real bug is context-mis-targeting, not raw capacity — the context-read is the
   primary lever, and the model-swap is the ceiling-raiser.
2. One small on-device model (2–4B, Q4-quantized) handling both register detection and
   generation is enough — no cloud, no 7B+.
3. On-device (email never leaves the Mac) is a hard requirement, the whole point.

All three were confirmed by the user.

## Approaches Considered

### Approach A: Context read, keep the 3B
Accessibility thread-reader + a keyword/emoji register detector feeding the existing 3B.
Effort S, risk low. Rejected as the final answer: register detection stays heuristic and
the 3B's documented word-salad risk remains.

### Approach B: Full local stack (Qwen3.5 on-device)
Same thread-reader + Qwen3.5-2B/4B (Q4) via an on-device runtime doing classify→generate,
replacing the 3B entirely. Effort L, risk medium. Cleanest match to all three premises.

### Approach C: Plus your own voice (personal corpus)
B plus a personal sign-off corpus from the user's own sent mail. Effort M on top of B,
risk medium-high. The true "whoa," but scans sent mail (its own privacy question) and adds
the most moving parts. Deferred.

## Recommended Approach

Approach B — full local stack, **two-pass (classify then generate) as primary**.

Model: Qwen3.5-2B/4B (Apache 2.0, 32K context; 2B vs 4B settled by the probe in Next Step
2). Gemma 4 E2B/E4B set aside (multimodal weights are dead weight for text); Phi-5 Mini set
aside (256K context is overkill for 8-word prose). Runtime (MLX vs llama.cpp) is settled by
the same probe.

**Cloud precedence: the local two-pass stack runs FIRST for the context-aware path.** The
shipping code is cloud-first — `GenerationService.swift:144` runs cloud generation whenever
any API key is configured, which would silently bypass the local stack (and the whole
on-device premise) for any BYOK user. The context-aware path therefore preempts cloud: the
thread-reader + classifier + local generate runs before any `CloudProviderWalk`, and cloud
is demoted to a non-context fallback (or removed from this flow). This is a deliberate
change to the current cloud-primary ordering.

### Why two-pass primary, not one-pass

The existing pipeline already assumes a register is known *before* generation: per-register
few-shot instructions, `ProviderResponseGuard.temperature(for:)` (`Providers.swift:187`),
and the inline mechanical gates in `GenerationService` (`mechanicalRejectReason`,
`GenerationService.swift:814` — near-duplicate/Jaccard dedup, skeleton and shape
collisions, banned tokens, length; the former `SignoffQualityValidator` type was removed
and folded into these inline checks) are all keyed on a register. So:

- **Call 1 — classify.** Thread text in, register string out (`standard|professional|
  unhinged`), temperature pinned at 0.2. Enforcement depends on backend: Foundation Models
  constrain the output via a `Generable` struct; llama.cpp/MLX produce a raw string that is
  parsed and matched against the three allowed values, any other string discarded (fall
  back to `standard`).
- **Call 2 — generate.** That register's existing instructions + `temperature(for:)`, one
  closing line out, validated by the mechanical gates.

A one-pass variant (classify+generate in a single call, returning
`{"register": "...", "signoff": "..."}`) is a post-probe *optimization* to try only if the
two-pass latency is unacceptable. It is not the primary shape, because folding
classification into generation complicates the validator (which expects a known register)
for no proven gain at 8 words of output.

### Worked two-pass example

```
Call 1 (classify):
  System: Choose the register of this email thread. Reply with exactly one of:
  standard, professional, unhinged.
  Thread: "On Sep 9, Priya wrote: Hi Arpit, Q3 came in low — can you send the revised
  forecast by EOD? — Priya"
  Draft:  "Hi Priya, on it now."
  Output: professional

Call 2 (generate):
  instructions = professional register instructions
  temperature  = ProviderResponseGuard.temperature(for: context) — context.bucketId = .professional
  prompt       = thread + draft
  Output: "Best regards,"
```

The thread-reader captures BOTH the quoted thread and the in-progress draft (the text
already typed in the composition field). If the draft is empty, generation proceeds on
thread alone.

### Code seam

A new `LocalModelProvider` plugs in behind the existing `sessionFactory` injection point
(`FoundationModelsSessionPool.sessionFactory`, a `@Sendable (String) -> any
LanguageModelSessionProtocol`). This is a *starting* seam, not a guaranteed drop-in. Two
concrete obstacles, sized during the Next Step 2 probe (Open Question 2):

- **The pool's `respond` is single-purpose for `SignoffOutput`.**
  `FoundationModelsSessionPool.respond` hardcodes `generating: SignoffOutput.self`
  (`FoundationModelsSessionPool.swift:86`). The classify pass needs a *second* respond path
  (its own `Generable` output type), not an adaptation of the existing one.
- **There is no UI → classify → generate entry point yet.** `generate(bucketId:)` takes the
  bucket from UI selection and is guarded by a single-flight `inflightRequest`
  (`GenerationService.swift:79`). The two-pass flow needs a new atomic entry point (classify
  then generate inside one call, or popover-orchestrated across two) that starts from the
  thread text, not a UI-chosen bucket.

The `Generable` structured-output contract has no direct analog in llama.cpp/MLX, which
produce raw strings; that translation is also settled by the probe.

## Error Paths

- **No thread text** (fresh email, non-mail focused window): fall back to `standard`.
- **AX permission denied**: one-time prompt to grant Accessibility; degrade to `standard`
  until granted. Never block generation on the read.
- **Classifier emits an out-of-range string**: discard, fall back to `standard`.
- **Call 2 returns malformed/undecodable output**: existing mechanical gates + retry loop
  already handle unsafe candidates; no new path.
- **Model weights missing/corrupt on launch**: detect at startup, surface a one-button
  re-download, and refuse generation with a clear message (never crash) until resolved.
- **Runtime load failure** (MLX/llama.cpp init error): same surfacing path as missing
  weights; the app remains usable for the existing 3B fallback.

## Open Questions

1. **Go/no-go gate — AX read reliability.** Can the Accessibility API read the focused
   composition window (including quoted prior messages) across Mail.app, Gmail, and
   Outlook, and does Superhuman's composition window expose AX text at all? Hard gate, not
   a de-risk step. Kill criterion: if AX can't read web-client composition reliably, fall
   back to a clipboard/manual-thread-copy path, and treat Superhuman as unsupported until
   proven otherwise.
2. **Second go/no-go gate — runtime + distribution.** Does Qwen3.5's Q4 GGUF download and
   load cleanly on MLX or llama.cpp within the 8GB budget, and does redistribution stay
   legal (Apache 2.0) at ~2GB bundle size? Same severity as the AX gate. Kill criterion: if
   either runtime can't load the weights and stream within budget, fall back to Approach A
   (heuristic detector + existing 3B) rather than shipping a broken local stack.
3. Qwen3.5-2B vs -4B (personality ceiling vs speed), and MLX vs llama.cpp — settled by the
   Next Step 2 probe.
4. **Thread-length policy.** Long quoted history is the dominant prefill cost. Cap the
   thread at the last 3 turns (or ~2,000 chars, whichever is smaller) before classify and
   generate. Exact cap tuned in the probe.

## Success Criteria

- Hit the shortcut, get a correct-register sign-off on the first try, with no word salad,
  no literal "comma," and no manual bucket selection.
- Generation stays on-device; email content never leaves the machine.
- Runs on 8GB M1 without swap thrash. Latency split by phase: thread prompt-processing
  (prefill of the capped thread) under ~2s — paid ONCE, not twice. The local runtime keeps
  one resident session and reuses the KV cache across the classify→generate passes, which is
  the native MLX/llama.cpp behavior; the two-pass flow must NOT copy
  `FoundationModelsSessionPool`'s fresh-session-per-`respond` constraint (that exists only
  to avoid Apple's transcript pollution, and mirroring it would make the local stack prefill
  the thread twice for no reason). ~8-word generation under ~500ms. Combined target:
  interactive (<3s worst case). Figures are provisional and validated by the probe; if
  prefill does not fit the budget, tighten the thread cap rather than accept a second prefill.

## Distribution Plan

Existing Homebrew formula (Signoff.rb) + macOS app bundle. Weights are lazy-downloaded on
first launch (small install, then a ~2GB Q4 download with progress and an offline fallback
to the existing 3B), rather than bundled at install. The formula re-hash updates as before.
No new CI/CD surface beyond the existing release build for the app bundle itself.

The weights ARE a new distributed artifact and get their own minimal surface: a stable
download host, a pinned weights version (the app targets one specific Q4 snapshot, so a
model change is a versioned release, not a silent swap), and a SHA-256 checksum verified
after download — a corrupt or truncated ~2GB download is detected and triggers re-download,
never loaded as garbage. This is the only addition beyond the existing release build.

## Tests

Each new codepath gets a test from the start (not deferred to a follow-up pass):

| Codepath | Test | Kind |
|---|---|---|
| Classifier emits `professional`/`standard`/`unhinged` | parse the classifier string, assert correct register | unit |
| Classifier emits an out-of-range / empty string | assert fallback to `standard` | unit |
| Register → instructions routing | assert each register maps to its existing instruction set | unit |
| Register → `temperature(for:)` | assert `context.bucketId` drives the right temperature per `Providers.swift:187` | unit |
| Two-pass orchestration | inject a mock `sessionFactory`; assert classify runs first, generate second, and generate receives the classified register | unit |
| AX thread-reader capture (thread + draft) | capture quoted thread and in-progress draft from a focused composition window | integration (gated by go/no-go #1) |
| Weights missing / corrupt on launch | assert a one-button re-download surface and no crash | unit |
| Runtime load failure (MLX/llama.cpp init) | assert fallback to existing 3B and a clear message | unit |

**Live-model concurrency caveat (already logged in gstack):** any suite that calls a live
on-device model (Foundation Models today, MLX/llama.cpp after the swap) must run serialized.
`FoundationModelsSessionPool` already serializes FMF generations, and the M1 on-device
runtime is single-stream — running two live-model suites concurrently produces instant
zero-result failures. Keep the pure-unit suites (classifier parse, routing, temperature,
error paths) as the fast regression gate, and gate the live-model suites behind go/no-go #2.

## Next Steps

1. Spike the thread-reader: Accessibility read of the focused composition window, capturing
   BOTH the quoted thread and the in-progress draft. This is go/no-go gate #1 — prove it on
   Mail.app + at least one web client before building anything else on top.
2. Stand up the on-device runtime with Qwen3.5-2B/4B (Q4); run the probe to (a) pick 2B vs
   4B, (b) settle MLX vs llama.cpp, (c) confirm weights load within the 8GB budget and
   redistribution stays legal (go/no-go gate #2), and (d) validate the latency figures and
   thread-length cap.
3. Wire a new `LocalModelProvider` behind the `sessionFactory` seam (adapting
   `LanguageModelSessionProtocol` if the backend requires it) — two-pass classify→generate
   as settled above.
4. Route the thread text through the classifier then the register's existing instructions
   + `temperature(for:)`; keep the mechanical gates and dedup windows as the safety net.
